# Mobile Kitchen — キッチンカー出店プラットフォーム

キッチンカーの **出店募集（主催者）** と **出店申込（出店者）** をひとつの画面にまとめた Web アプリです。
出店者はイベントをスワイプで見て、その場で申し込めます。主催者はイベントを公開し、申込を受け取り、
募集案内のメール文面をワンタップで生成できます。

- スマートフォン前提の UI（スワイプ + タップ）
- 引き算のデザイン / ライト・ダーク対応。アイコンはすべて自前のSVG（絵文字は不使用）
- ログイン不要で出店申込、主催者のみログイン
- データは Supabase（Postgres + Storage）で管理。RLS で出店者と主催者の権限を分離

---

## 画面

### 出店者ページ `#/vendor`

| 機能 | 内容 |
| --- | --- |
| さがす | 募集中イベントをカードデッキで1件ずつ表示。**右スワイプ = 申し込む／左スワイプ = 見送る／タップ = 詳細**。誤操作は「戻す」で1件ずつ取り消せます |
| 枠の表示 | すべてのカード・詳細・申込画面に**枠の埋まり具合メーター**を表示。先着は「残り◯枠」、抽選は「倍率◯倍」 |
| 申込フォーム | 6ステップ（店舗情報 → 火気 → 電気 → 出店内容 → 書類 → 確認）。横スワイプでもステップを移動できます |
| 申込状況 | 自分が申し込んだイベントを一覧。申込内容は本人にもサーバから読み戻せない設計のため、端末に残した控えを表示します |

入力内容は端末に保存され、**2回目以降の申込は自動入力されます**。

### 管理者ページ `#/admin`

| タブ | 内容 |
| --- | --- |
| イベント | 一覧・新規作成・編集・公開/締切の切替・削除。申込数と充足率をその場で確認 |
| 出店者 | 申込の一覧・検索・詳細・承認/見送り・**CSV書き出し**（消防署提出や台帳作成にそのまま使えます）。抽選イベントでは**抽選の実行**もここから |
| メール | **募集中イベントを複数選んで、案内メールの文面を自動生成**。4種類のテンプレートから選択、その場で編集してコピー |
| 設定 | データ保存先（端末内 / Supabase）の切替、スキーマSQLのコピー、外観（自動/ライト/ダーク） |

## 収集する情報

### イベント（主催者が入力）

タイトル / 概要 / サムネイル画像（任意） / 開催日時 / 営業時間 / 搬入時刻 / 会場名 / 住所 /
出店料・補足 / 電源の有無・1区画の供給上限(W) / 給排水 / **募集枠数** / **選考方法（先着順・抽選）** /
想定来場者数 / 申込締切 / **抽選結果の通知予定日** / 主催者名 / 問い合わせ先 / キャンセルポリシー /
備考 / 添付資料（PDF等） / 公開状態

### 出店申込（出店者が入力）

- 店舗名 / 代表者名 / メールアドレス / 電話番号
- 火気使用の有無
  - ガスの場合：種類（プロパン / カセットボンベ / その他）・本数・1本あたり容量
  - 炭の場合：**消火方法**
  - 消火器の携行本数
- 電気を使用する機器（**名称・消費電力・台数を機器ごとに追加**、合計Wを自動計算し会場の上限超過を警告）
- 発電機の持込有無・機種
- 提供メニュー（名称・価格、複数追加可）
- キッチンカーサイズ（全長・全幅・全高／**展開時**の全長・全幅）
- 車両ナンバー / 食品営業許可番号 / PL保険の加入有無
- ファイル添付（免許証・車検証・営業許可証など、PDF/画像）
- 主催者への連絡事項

> 元の要件に加えて、**消火器の本数・発電機・展開時サイズ・営業許可番号・PL保険・搬入時刻・想定来場者数・キャンセルポリシー**
> を追加しています。いずれも現場で毎回聞き直しが発生しやすい項目です。

## 募集枠と選考方法

イベントには **募集枠数** を設定します。埋まり具合は出店者側（カード・詳細・申込画面）と
主催者側（イベント一覧・抽選パネル）で**同じメーター・同じ数字**を見るようにしてあり、
表示ロジックは `src/components/CapacityMeter.tsx` の1箇所だけです。

選考方法は2種類あり、**枠が埋まったときの挙動が決定的に違います**。

| | 先着順 | 抽選 |
| --- | --- | --- |
| 枠が埋まったら | **募集終了**（出店者のカードデッキから消える） | **締切まで受付を継続**（応募が積み上がる） |
| メーターの読み | 残り◯枠 / 満了 | 全◯枠に◯件の応募 / 倍率◯倍 |
| 強調バッジ | 残りわずか（2枠以下 or 80%以上） | 応募多数（倍率1倍超え） |
| 申込ボタン | 「この内容で出店を申し込む」 | 「この内容で抽選に応募する」 |
| 完了画面 | 申込を受け付けました | 抽選に応募しました（結果通知日を表示） |
| 決定 | 先着＝申込順に確定 | 主催者が「出店者」タブから**抽選を実行** |

抽選の実行は、確認待ちの応募から残り枠数ぶんを Fisher–Yates で無作為抽出し
（乱数は `crypto.getRandomValues`）、当選を承認・落選を見送りに一括更新します。
承認済みの応募は確定枠として残し、残りの枠だけを抽選対象にします。
締切前に実行しようとした場合は警告を出します。

## UI の設計意図

Apple 的な「引き算」を土台に、行動経済学の知見を申込導線へ落としています。

| 仕掛け | 置き場所 | 狙い |
| --- | --- | --- |
| 1画面1イベントのカードデッキ | さがす | 選択肢を並べるほど人は決められなくなる（選択のパラドックス）ため、判断を右か左かに単純化 |
| 「残り◯枠」「締切あと◯日」 | カード・詳細・申込 | 希少性と締切効果（先着） |
| 「倍率◯倍」「応募多数」 | カード・詳細・申込 | 競争の可視化。埋まっても締め切らない抽選では、これが希少性の代わりになる |
| 「全◯枠に◯件の応募」 | 全画面共通のメーター | 社会的証明。他店が動いていることが数字で見える |
| 埋まり具合メーター | カード・詳細・申込・管理一覧・抽選パネル | 数字より「あとどれだけ残っているか」が直感的 |
| 「戻す」「やっぱり見る」 | 見送り直後 | 取り消せると分かると、人は決断に踏み切れる |
| ステップ進捗と「あと◯ステップ」 | 申込フォーム | 目標勾配効果。残りが見えるほど完走率が上がる |
| キャンセルポリシーの明示 | 詳細・最終確認 | 損失回避の緩和 |
| 完了アニメーション + 次の行動 | 申込完了 | ピーク・エンドの法則 |
| 入力内容の自動保存 | 全体 | 2回目以降の摩擦をほぼゼロに |

配色は面＝白・線＝極細・色は1色（アクセント）に限定し、強調は色ではなく余白と階層で作っています。

## データベース（Supabase）

データは Supabase（Postgres + Storage）で管理します。

### テーブルの命名

この Supabase プロジェクトは **他サイトと共用** しているため、当サイトの資産はすべて
`ft_`（food truck）で始めます。他サイトのテーブル（`kc_events` など）には一切触れません。

| 種別 | 名前 |
| --- | --- |
| テーブル | `ft_events` / `ft_applications` |
| ビュー | `ft_event_application_counts` |
| ストレージバケット | `ft-attachments` |

識別子は `src/lib/db/names.ts` の 1 箇所にまとまっているので、変更はそこだけで済みます。

### セットアップ（初回のみ・5分）

1. **スキーマを適用する**
   [`supabase/schema.sql`](supabase/schema.sql) の内容を Supabase の **SQL Editor** に貼り付けて実行します。
   （管理者ページ → 設定 → 詳細設定 → 「スキーマSQLをコピー」からも同じ内容を取得できます）
   テーブル・インデックス・RLSポリシー・集計ビュー・ストレージバケットが作られます。
   すべて `create if not exists` / `create or replace` なので、既存のテーブルには影響しません。

2. **主催者アカウントを作る**
   Supabase の **Authentication → Users → Add user** でメールアドレスとパスワードを登録します。
   管理者ページはこのアカウントでログインします。

以上で、出店者はログインなしで申込でき、主催者はログインして管理できる状態になります。

### 権限の設計（RLS）

| 対象 | 誰でも（未ログイン） | 主催者（ログイン済み） |
| --- | --- | --- |
| 公開済みイベント | 閲覧 | 閲覧・作成・編集・削除 |
| 下書きイベント | — | すべて |
| 出店申込 | **送信のみ** | 閲覧・承認・見送り・削除 |
| 申込件数 | 件数のみ閲覧 | 〃 |
| 添付ファイル | 閲覧・アップロード | 〃 |

出店者は他店の申込内容を読めません（自分の申込も読み戻せません）。
ただし残枠・充足率の表示には件数が必要なため、件数だけを集計した
`ft_event_application_counts` ビューを公開しています。
出店者側の「申込状況」タブは、送信時に端末へ残した控えを表示します。

ポリシーは `auth.role()` のようなヘルパに依存せず、`to anon` / `to authenticated` の
ロール単位で定義しています。`supabase/schema.sql` は実際の PostgreSQL 16 に対して
適用・再適用・権限検証を通してあります（冪等・カスケード削除・件数ビューを含む）。

publishable key はブラウザに配られる前提のキーで、実際の保護は上記の RLS が担います。

### 端末内モード

Supabase に書き込まずに操作を試したいときは、管理者ページ → 設定 → 詳細設定 →
「端末内モードで動かす」で IndexedDB に切り替えられます（サンプルイベント付き）。
その端末の中だけで完結し、Supabase には一切影響しません。

## 構成

```
supabase/schema.sql   テーブル・RLS・ストレージの定義（SQL Editor に貼る実体）
supabase/seed-events-2026-10.sql  イベント登録用SQL（再実行しても重複しない）

src/
  lib/
    types.ts          ドメインモデル
    db/               データアダプタ（契約 / Supabase / IndexedDB）
      names.ts        テーブル・バケット名（サイト識別子 ft_ はここだけ）
    store.tsx         React コンテキスト。取得と更新を集約
    format.ts         表示整形と、残枠・倍率・締切などの導出ロジック
    mailTemplate.ts   複数イベント → メール文面の生成
    csv.ts            申込のCSV書き出し
    schemaSql.ts      supabase/schema.sql を読み込むだけの薄い橋渡し
    seed.ts           端末内モード用のサンプルデータ
  components/         UIプリミティブ、シート、トースト、イベントカード、枠メーター
    icons.tsx       画面で使うSVGアイコン一式（24×24・線幅1.6・currentColor）
  pages/
    Landing.tsx
    vendor/           さがす（デッキ）/ 申込フォーム / 申込状況
    admin/            イベント / 出店者（抽選の実行を含む）/ メール / 設定
```

バックエンドは `DataAdapter` の 1 インターフェースに閉じているので、
Supabase 以外（Firebase、自前 API など）へ差し替える場合も実装を 1 ファイル足すだけで済みます。
